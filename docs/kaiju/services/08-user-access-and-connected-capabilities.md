# User access and connected capabilities

Use these branches only when the agreed journey includes the capability. They extend the seven service cards; they do
not make every Kaiju app an OAuth, CMS or MCP project. The supplied
[retrospectives](../failures/retrospectives/README.md) explain the observed gaps.

| Capability                           | Inputs and owner                                                                                                                                                         | Acceptance and failure handling                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First administrator and staff access | App owner identifies the current account, secure retrieval path, accepting person and available session/consent.                                                         | Prove the intended sign-in/setup route. Treat a stale bootstrap password or refused interactive sign-in as an explicit test limit. Preserve real accounts; do not reset passwords or bypass consent for convenience.                                                                                                                                                                  |
| Staff OAuth                          | Identity/app owners supply the registered client, complete credential pair, encrypted storage classification, callback origins, feature flag and allowed account policy. | Trace source through launch audit, injection and redaction before tagging. Exercise the real auth library/database, rejected identities, account linking and simultaneous callbacks while preserving IDs/roles and intended password access. A group address is not an individual OAuth identity. Disabled signup or a disabled provider does not by itself revoke existing sessions. |
| Cross-repository website activation  | Owners record each repository/ref, environment input, CMS publication, built artifact and production route.                                                              | Track code merged, settings applied, content valid/published, build deployed and runtime fetch verified separately. Check the public URL and failure/empty/cache behavior. Define which owner reverses each activation step; an environment flag alone does not deploy an absent adapter.                                                                                             |
| Content migration and MCP            | Content owner approves the source/destination, incomplete records, schema requirements, write scope and actual client.                                                   | Validate drafts before proposing import; do not invent missing employment terms or other business facts. Use stable mappings, conflict detection and read-back for writes. Public list/read tools do not establish private editing, OAuth consent or actual ChatGPT/Claude compatibility. Keep intentionally incomplete content intact.                                               |
| Public presentation                  | App/design owner defines the minimum agreed browser journey and supported environments.                                                                                  | Check the built anonymous route, narrow/desktop layouts, keyboard/form/upload state, portals, failed retries, asset bytes/licence access and relevant clock/timezone differences. An HTTP success that serves login HTML is not proof that a public asset loaded. Apply only the supported browser cases relevant to the change.                                                      |

For every branch, record implemented, published, activated and accepted states with their exact evidence. A later
requested feature is legitimate new scope; it must receive its own acceptance contract without rewriting the history of
the first launch.
