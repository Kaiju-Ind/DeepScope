# Overview

A project should produce useful knowledge about a customer problem before large implementation work begins. Identify
the next product decision, ask what remains unknown, and test the smallest piece that can resolve it. The result becomes
an anchor: a scoped observation the team can use to choose its next action. Follow the
[product method](../product/README.md) throughout research, delivery and review.

For implementation, the repeatable unit is a small product change with known owners, verified contracts and an observed
customer result. A usable preview and production promotion apply when deployment is part of the requested outcome. A
library, local tool or research task can have a different acceptance path.

The [generic profile](../profiles/generic.md) is the default. This handbook preserves ItsAPlan, OpenATS, Grafana,
Twenty and Core examples with exact source identities. Their Kaiju packages and platform choices apply only through
the [Kaiju profile](../profiles/kaiju.md) or a matching verified project contract. Proposed automation is not an
implemented capability, and historical evidence does not establish current behavior.
